# 公民組織的 GitHub 資源搜尋與選擇指南：從流程拆解到 AI 時代的版本管理

> 90 分鐘課程｜講義與簡報製作需求文件

## 1. 課程定位

本課程不是 Git 指令課，也不以「教完 GitHub 所有功能」為目標。課程有三個並重的主軸：

1. **流程規劃與拆解**：先把組織的工作拆成步驟，找出真正要改善的那一步，再談工具。
2. **GitHub 的用途與版本控制**：理解 GitHub 為什麼存在，尤其在 AI 頻繁修改檔案與程式的時代，為什麼需要「能回頭的修改紀錄」。
3. **資源搜尋與選擇**：把需求轉成搜尋關鍵字，找到資源後初步評估是否適合組織使用。

**課程主線：**

```text
組織遇到的問題
→ 拆解現行流程，找出要改善的步驟
→ 理解 GitHub 與版本控制能幫上什麼
→ 判斷需要哪種資源，在 GitHub 搜尋與取得
→ 用 AI 協助理解
→ 評估是否適合導入
```

**課程核心句：**

> 先做使用者訪談（針對利害關係人去做焦點訪談），先拆流程，再找工具，設計流程。
>
> AI 讓修改變容易，版本控制讓修改可以回頭。
>
> 找得到，不等於能直接用；下載得到，不等於適合組織長期使用。

## 2. 目標對象與需求

### 目標對象

- 公民團體、非營利組織與基金會工作者。
- 以非技術背景、初次接觸 GitHub 者為主要受眾。
- 兼顧已有 WordPress、QGIS、Airtable、GAS、n8n 或自行開發小工具經驗的參與者。

### 報名者常見需求

| 類型 | 具體問題 |
|---|---|
| 行政與活動 | 報名、名冊、出勤、核銷、成果統計重複整理 |
| 文件與交接 | 檔案版本混亂、文件共享、知識保存 |
| 資料管理 | 志工、校友、會員、捐款人與服務對象資料 |
| 網站與內容 | 官網維護、WordPress、電子報、網頁更新 |
| 開放資料 | 政府資料整理、統計、地圖應用 |
| AI 與自動化 | AI 工具、GAS、Python、n8n、AI 產生程式碼的管理 |

### 需要正面回應的顧慮

- 資訊安全與個人資料保護。
- 開源授權與使用限制。
- 操作門檻與技術人力。
- 安裝、更新、備份及後續維護。
- 工具免費之外的實際成本。

以上需求與顧慮整理自報名單位交流內容工作表。

## 3. 學習目標與課程邊界

課程結束後，參與者應能：

1. 用流程拆解表，把一項組織工作拆成步驟，標出誰做、用什麼工具、經手哪些資料，以及最卡的是哪一步。
2. 判斷每個卡關的步驟適合「先改流程」「找現成資源」「交給 AI 協助」，或「暫時不動」。
3. 用白話說明 GitHub 的用途，並看懂 Repository、README、檔案、授權及修改紀錄。
4. 用「存檔點」的比喻說明版本控制（Commit、History、Diff、Revert），以及它為什麼在 AI 時代特別重要。
5. 分辨哪些東西適合放上 GitHub，哪些絕對不能放（個資、密鑰、帳號設定）。
6. 把需求轉換成資源類型與中英文搜尋關鍵字。
7. 看懂搜尋、閱讀與取得公開範例資源的步驟，課後能照講義自行操作一次。
8. 用 AI 協助理解公開專案說明，同時回到原始資料核對。
9. 判斷下一步是先整理流程、自行試用，或尋求技術協助。

**本課程不承諾完成：**

- 建置 CRM、捐款或個案管理系統。
- 完成 AI 模型訓練、自動化串接或系統部署。
- 教會每位學員 Git 指令與程式開發。
- 保證某個 GitHub 專案安全、合法或適合直接導入。

## 4. 開課單位承諾的對應方式

| 開課資訊中的承諾 | 課程如何交付 |
|---|---|
| 掌握基本術語、看懂基本資訊 | 帶學員閱讀一個 Repository，而非逐項介紹整個平台選單 |
| 從組織需求練習搜尋與下載 | 以真實工作情境產生關鍵字，搜尋並取得低門檻公開範例 |
| AI 協作分析專案能否解決問題 | 示範 AI 解讀 README，區分文件事實與 AI 推測 |
| 理解文件、資料與網站如何公開及更新 | 以版本控制單元說明修改紀錄如何保存與回復，並說明存放檔案和發布網站的差異 |

## 5. 案例規劃

### 主案例：活動資料與固定報表

**情境：**組織每月舉辦活動，報名資料散落在表單與試算表中，每次都要手動製作固定格式的統計圖表或成果資料。

**教學目的：**

- 用流程拆解找出真正需要改善的是哪一段工作。
- 讓學員看到：不同步驟的解法不同，不是每一步都需要新工具。
- 分清楚「文件範本」「資料整理方法」「程式工具」「完整系統」。
- 示範搜尋、閱讀 README、取得範例與初步評估。
- 使用虛構資料，避免接觸真實參與者個資。

**流程拆解示範：**

原始說法：「每次活動結束都要重新整理報名資料，很花時間。」拆開後如下（耗時為示意）：

| # | 步驟 | 誰做 | 工具 | 經手資料 | 耗時 | 卡在哪 | 解法方向 |
|---|---|---|---|---|---|---|---|
| 1 | 建立報名表單 | 承辦人 | Google 表單 | — | 30 分 | 每次重做欄位 | **範本**：複製上次的表單 |
| 2 | 匯出報名資料 | 承辦人 | Google 試算表 | 姓名、電話、Email | 10 分 | — | 不用動 |
| 3 | 清理欄位、去除重複 | 承辦人 | Excel | 同上（個資） | 60 分 | 格式不一、重複報名 | **AI 協助**寫公式（只給欄位名稱與假資料） |
| 4 | 對照簽到、計算出席 | 志工 | 紙本簽到表 → Excel | 同上（個資） | 60 分 | 手抄錯誤 | **先改流程**：改用表單或 QR 簽到 |
| 5 | 製作統計圖表 | 承辦人 | Excel | 去識別的統計數字 | 45 分 | 每次重畫圖 | **找現成資源**：圖表範本（chartjs-bar） |
| 6 | 撰寫成果報告 | 主管 | Word | 統計結果 | 60 分 | 「最終版_v3」版本混亂 | **版本控制**觀念 |

教學重點：
- 拆完才發現，第 4 步要改的是流程，不是找工具；第 5 步才需要上 GitHub 找資源。
- 個資只出現在第 2–4 步，所以這幾步不要交給線上工具或 AI 處理真實資料。
- 簡報用**泳道圖**呈現（承辦人／志工／主管三條泳道），讓學員看到工作在誰手上交接；學員在紙本上用**流程拆解表**填寫自己的流程。

**搜尋示範：把需求句拆成「資源類型＋工具名稱」**

直接用需求句搜尋幾乎找不到結果；這個落差本身就是教學點。（2026-10-01 實測）

| 搜尋詞 | 結果 | 說明 |
|---|---|---|
| `event registration report template` | 0 筆 | 需求句太具體 |
| `nonprofit volunteer spreadsheet template` | 0 筆 | 同上 |
| `活動 報名` | 有結果，但多為工程師開發的報名系統 | 中文詞能搜到，但資源類型不符 |
| `google sheets template`、`chart template csv` | 出現可用的範本 | 改用「工具名稱＋資源類型」 |

**示範資源（已驗證，2026-10-01）**

| 用途 | Repository | 授權與維護 | 教學重點 |
|---|---|---|---|
| 方法文件類 | [HandsOnDataViz/book](https://github.com/HandsOnDataViz/book) | GitHub 標示 MIT，README 卻寫書本內容採 CC BY-NC-ND 4.0；最後更新 2026-06 | 寫給非程式背景讀者的開放書，有資料清理、樞紐分析、做圖章節。**授權標籤不等於全部內容的授權，要讀 README**；README 也註明不提供安裝或技術支援 |
| 範本類（主案例） | [HandsOnDataViz/chartjs-bar](https://github.com/HandsOnDataViz/chartjs-bar) | **無 LICENSE**；最後更新 2021-04 | 把 `data.csv` 換成活動統計，就能產生長條圖，另有線上 demo。可以示範三件事：能看懂、能下載，但沒有授權不能直接改用；更新停在 2021 年；下載 ZIP 後雙擊 `index.html`，圖表會是空白（需要網頁伺服器），而 `data.csv` 用 Excel 就能打開 |
| 已淘汰的舊版本 | [HandsOnDataViz/chartjs-templates](https://github.com/HandsOnDataViz/chartjs-templates) | 無 LICENSE；最後更新 2020 | README 寫「已拆分成獨立 repo」，示範如何從 README 發現「這裡已經不是最新版」 |

> 示範時以講師操作為主（學員現場沒有電腦），所有畫面都要準備截圖作為備案。

### 對照案例：校友或捐款人 CRM

**情境：**在 GitHub 找到一個看似功能完整的 CRM 專案。

**教學目的：**讓學員理解，找到程式碼不等於可以立即導入；仍須評估資料權限、部署方式、更新、備份、授權與維護人力。

**示範資源：**[civicrm/civicrm-core](https://github.com/civicrm/civicrm-core)（AGPL-3.0，持續更新中）。README 中可看到的評估線索：

- 專為倡議與非營利組織設計，看起來完全符合需求。
- 必須以獨立 PHP 網站形式運作，或安裝在 WordPress、Drupal 等系統中，也就是需要主機與資料庫。
- 下載與安裝都導向官網和系統管理員手冊，而不是 GitHub 上的 Download 按鈕。
- 列出付費支援廠商：免費授權不等於零成本。
- AGPL 授權：修改版若透過網路讓別人使用，須向這些使用者提供原始碼；實際要求依整合方式而定，請技術或法務人員確認。

不批評專案品質；重點是「它很成熟，但導入需要的條件，組織有沒有」。

### 版本控制情境：AI 時代為什麼需要「能回頭的修改」

報名資料中已有團體提到「檔案版本混亂」與「AI 產生程式碼的管理」。這個單元只講觀念與比喻，不操作 GitHub，必要時用靜態截圖輔助。

**三個開場情境：**

1. **檔名地獄：**「活動報表_最終版_v3_真的最終.xlsx」，沒人知道哪個才是對的。
2. **AI 改壞了：**請 AI 修改 GAS 報表腳本，改到第五次壞掉，卻回不去能用的那一版。
3. **交接斷線：**承辦人離職，沒人知道這段公式是誰、在什麼時候、為什麼改的。

**存檔點比喻：**

| GitHub 用語 | 遊戲比喻 | 白話說明 |
|---|---|---|
| Commit | 存檔 | 存下目前狀態，並寫一句「這次改了什麼」 |
| History | 存檔清單 | 依時間列出每一次存檔與說明 |
| Diff | 比較兩個存檔 | 用紅綠標示哪幾行被刪除、哪幾行被新增 |
| Revert | 讀取舊存檔 | 回到改壞之前的版本 |

**要講清楚的觀念：**

- **你其實已經在用版本控制：**Google 文件的「版本記錄」就是一種。GitHub 的不同在於：每次存檔都要寫說明、能逐行比較差異、能多人同時修改再合併。
- **AI 時代更需要它：**AI 一次可能改幾十行，人很難用肉眼看出改了什麼。有版本紀錄，就能看到 AI 改了哪裡，改壞了也能回頭。許多 AI 寫程式工具也能直接整合 Repository；不管在哪裡修改，都先存檔、再看差異。
- **公開與更新：**Repository 裡的檔案，和用 GitHub Pages 發布的網站是兩回事。以 [leaflet-maps-with-google-sheets](https://github.com/HandsOnDataViz/leaflet-maps-with-google-sheets) 為例，並列比較 repo 檔案和網站。
- **什麼不能放上 GitHub：**報名名單、個資、API 金鑰、帳號密碼。私人 Repository 也不適合放個資。適合放的是程式碼、範本、公開文件與去識別資料。上傳 AI 寫的小工具前，要先檢查有沒有寫死的密鑰與帳號設定。

## 6. 90 分鐘流程

| 時間 | 單元 | 教學內容與產出 |
|---|---|---|
| 0–8 分 | 從組織問題開場 | 展示報名者常見情境；請學員判斷是流程、資料或工具問題 |
| 8–25 分 | **流程規劃與拆解** | 用泳道圖講解主案例；示範流程拆解表與「解法方向」；學員用紙本拆解自己組織的一項工作（約 8 分鐘） |
| 25–42 分 | **GitHub 的用途與版本控制** | GitHub 是什麼、不是什麼；看懂 Repository；三個版本混亂情境、存檔點比喻、AI 時代的必要性；repo 檔案與網站發布的差異；什麼不能上傳 |
| 42–58 分 | 搜尋與取得資源 | 講師示範「需求句搜尋 0 筆 → 換詞 → 篩選 → 打開 chartjs-bar → 下載 ZIP」；學員把拆解表中「找現成資源」的步驟寫成關鍵字 |
| 58–68 分 | AI 協作判讀 | 講師請 AI 解讀 HandsOnDataViz/book 的 README；學員對照講義上印出的 README，圈出 AI 說錯或推測的地方（例如授權） |
| 68–80 分 | 選擇與風險 | 以 civicrm-core 的 README 檢查個資、授權、操作、維護與成本 |
| 80–90 分 | 個人判斷與收束 | 學員回到自己的拆解表，勾選下一步；說明自行嘗試與尋求協助的分界 |

> 學員現場沒有電腦：全程由講師操作示範，學員以紙本填卡。每個示範畫面都要準備截圖，以防網路不穩。

## 8. 講義製作清單

講義不應只是簡報的縮印版；要讓學員回到組織後，仍能按步驟重做。

### 8.1 白話術語表

至少包含：

| 術語 | 講義中的白話解釋方向 |
|---|---|
| Repository | 一個專案放置檔案與紀錄的地方 |
| README | 專案的使用說明與入口 |
| LICENSE | 說明資源使用、修改或散布條件的授權資訊 |
| Issue | 記錄問題、需求或待辦事項 |
| Commit | 存檔：存下目前狀態，並寫一句這次改了什麼 |
| History | 存檔清單：每一次修改的時間、人與說明 |
| Diff | 比較兩個版本：紅色是刪掉的，綠色是新增的 |
| Revert | 讀取舊存檔：回到改壞之前的版本 |
| GitHub Pages | 把 Repository 裡的檔案發布成網站 |
| Download／Code | 取得檔案或專案內容的入口 |

### 8.2 流程拆解表

講義印成橫式表格，至少留 6 列空白。

```text
組織名稱或工作情境：＿＿＿＿＿＿＿＿＿＿＿＿
這項工作的最終產出是：＿＿＿＿＿＿＿＿＿＿＿

| # | 步驟 | 誰做 | 用什麼工具 | 經手哪些資料（個資打★） | 大約耗時 | 卡在哪 | 解法方向 |
|---|------|------|-----------|------------------------|---------|-------|---------|
| 1 |      |      |           |                        |         |       |         |
| 2 |      |      |           |                        |         |       |         |
| … |      |      |           |                        |         |       |         |

解法方向代號：
```

### 8.4 版本控制小抄

- 存檔點比喻：Commit／History／Diff／Revert（見 §5 版本控制情境）。
- 好的修改說明怎麼寫：「修正出席率公式，排除重複報名」優於「更新」。
- 請 AI 修改檔案前先存檔；AI 改完後先看差異，再決定要不要保留。
- 不能上傳 GitHub 的清單：個資、報名名單、API 金鑰、帳號密碼、內部財務資料。

## 10. 公司與服務露出

### 建議定位

> 我們協助組織從工作流程與實際需求出發，評估合適的開源及數位工具，並規劃網站、資料整合、自動化與後續維護。

### 露出方式

- **開場約 1 分鐘：**介紹講師背景與平時協助組織解決的問題。
- **案例進行時：**用「實務上會如何判斷」展現方法，不插入銷售頁。
- **結尾約 2–3 分鐘：**說明哪些問題可自行處理、哪些問題需要協助。
- **講義最後一頁：**清楚標示公司服務、聯絡方式及 QR code。

### 建議主推服務

**公民組織數位工作流程與開源工具評估**

可作為課後合作的入口。服務說明聚焦於一項具體工作：釐清流程、比較可能方案、辨識資料與維護風險，再決定是否需要網站建置、系統整合、自動化或教育訓練。未確定實際交付範圍前，不在課堂承諾免費診斷、固定時數或特定成效。

**結尾話術草案：**

> 今天的流程拆解表、搜尋方法與判斷表，大家可以帶回組織自行使用。如果你們已找到可能的資源，卻卡在流程整理、工具選擇、網站串接或後續維護，也可以帶著一項具體工作流程與我們討論。我們會先釐清問題，再判斷是否真的需要建置新工具。
