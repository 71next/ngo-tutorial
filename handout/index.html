01白話術語表

術語白話解釋
Repository（repo）一個專案放檔案與修改紀錄的地方，像一個會記住所有修改的資料夾。
README專案的說明書與入口。打開一個專案，先讀它。
LICENSE授權：說明可以怎麼使用、修改或分享。沒有 LICENSE ＝ 作者保留權利，不能直接拿來改用。
Issue記錄問題、需求或待辦事項的討論串。看得出專案有沒有人在回應。
Commit存檔：存下目前的狀態，並寫一句「這次改了什麼」。
History／Commits存檔清單：每一次修改的時間、修改的人與說明。看最後更新時間就在這裡。
Diff比較兩個版本的差異：紅色是刪掉的、綠色是新增的。
Revert讀取舊存檔：回到改壞之前的版本。
GitHub Pages把 repo 裡的檔案發布成一般人可以瀏覽的網站。
Code 按鈕／Download ZIP取得專案檔案的入口：按綠色 Code 按鈕，選 Download ZIP 下載壓縮檔。
Star使用者的「收藏」。數量多代表受關注，不代表適合你、也不代表安全。

04版本控制小抄

版本控制要解決三件事：檔名地獄（哪份才是最終版？）、AI 改壞了回不去、交接時沒人知道誰改了什麼。

存檔點比喻

GitHub 用語遊戲比喻白話說明
Commit存檔存下目前狀態，並寫一句「這次改了什麼」
History存檔清單依時間列出每一次存檔與說明
Diff比較兩個存檔紅色是刪掉的、綠色是新增的
Revert讀取舊存檔回到改壞之前的版本
💬 修正出席率公式，排除重複報名（示意） - 出席率 = 出席人數 / 報名人數+ 出席率 = 出席人數 / 不重複報名人數

一次存檔 ＝ 一句說明＋看得見的修改內容。

好的修改說明

✓「修正出席率公式，排除重複報名」
✓「成果報告新增 9 月活動照片說明」
✗「更新」　✗「改一下」　✗「final」

你其實已經在用

Google 文件的「版本記錄」就是一種版本控制。GitHub 多了三件事：每次都寫說明、逐行比較差異、多人改完再合併。

請 AI 修改檔案或程式時

① 先存檔　→　② 請 AI 修改　→　③ 看 Diff：AI 改了哪幾行？　→　④ 保留，或讀回存檔

AI 一次可能改幾十行，肉眼看不出來；有版本紀錄，就能看清楚，也能回頭。

絕對不能放上 GitHub

  • 報名名單、會員、捐款人、個案等個資：原則上不放，私人 repo 一樣有外洩風險；真的有需要，先找人評估
  • API 金鑰、帳號密碼、寫死在程式裡的設定（上傳 AI 寫的 GAS 或 Python 前先檢查）
  • 內部財務資料

適合放的是：程式碼、範本、公開文件、去識別資料。

放檔案 ≠ 發布網站

Repository 放的是檔案與修改紀錄；用 GitHub Pages 才會變成大家看得到的網站。範例：github.com/HandsOnDataViz/leaflet-maps-with-google-sheets（檔案）與 handsondataviz.github.io/leaflet-maps-with-google-sheets（網站）。

09AI 提示詞（可直接複製使用）

A. 判讀一個 GitHub 專案

我是沒有專職工程師的公民團體工作者。請只根據以下公開的 GitHub 專案 README，用繁體中文協助我判讀： 1. 這是文件範本、公開資料、程式工具，還是需要安裝的完整系統？ 2. 它想解決什麼問題？適合什麼使用情境？ 3. 使用前需要哪些技能、設備或維護工作？ 4. 如果組織可能用它處理活動參與者資料，還有哪些資安、個資、授權或成本問題尚未確認？ 5. 請將「README 明確寫出」與「你的推測」分開；資料不足時，請說不知道。 README 內容：＿＿＿＿＿＿＿＿＿＿＿＿

B. 把需求轉成搜尋詞

我在公民團體工作，想改善這個工作步驟：＿＿＿＿＿＿（例如：每月活動結束後，把出席統計做成長條圖）。 請幫我想 5 組可以在 GitHub 搜尋的英文關鍵字，格式是「資源類型＋工具名稱」（例如 chart template csv）。 只要給關鍵字和簡短理由，不要直接推薦專案連結。

為什麼不要 AI 直接推薦連結？因為 AI 可能編造不存在的專案。關鍵字請自己拿去搜尋，搜到的專案再點開確認。

C. 請 AI 修改檔案前後

請修改以下公式／程式：＿＿＿＿＿＿ 修改完成後，請逐項列出你改了哪些地方、為什麼改，並提醒我有沒有需要另外測試的地方。

修改前先存檔（Commit）；改完先看差異（Diff），確認沒問題再保留。

使用原則
  • 只貼公開資訊與虛構資料，不貼真實個案、捐款人、會員或活動參與者資料。
  • 需要範例資料時，只給欄位名稱，或用假名、假電話自行造幾筆。
  • AI 的回答一定要回到原始文件核對，特別是授權與安裝需求。

10課後重做指南

回到組織後，照著下面的步驟自己做一次。預計 30–60 分鐘。

步驟 1｜拆流程（15 分鐘）

找一位同事，一起把第 4 頁的流程拆解表填完。特別標出：卡關的步驟、經手個資的步驟（★）。

步驟 2｜想搜尋詞（5 分鐘）

只挑解法方向標「找」的那一步，用「資源類型＋工具名稱」寫出 2–3 組關鍵字。可以用第 10 頁的提示詞 B 請 AI 協助。

步驟 3｜在 GitHub 搜尋（10 分鐘）

  • 打開 github.com，在最上方的搜尋框輸入關鍵字，按 Enter。
  • 左側選 Repositories；右上角排序可改成 Recently updated（最近更新）。
  • 搜不到就換詞：拿掉太具體的字、改用英文、換一個工具名稱。

步驟 4｜讀一個專案（10 分鐘）

點開一個看起來合適的結果，填第 7 頁的 Repository 閱讀卡。重點看：README、LICENSE、最後更新時間。

步驟 5｜取得檔案（5 分鐘）

  • 按綠色 Code 按鈕 → Download ZIP → 解壓縮。
  • 先打開資料或範本檔（例如 .csv、.xlsx、.docx）。
  • 網頁類專案直接雙擊 index.html 可能是空白的，這很正常，看 README 有沒有線上 demo。

步驟 6｜判斷下一步（5 分鐘）

用第 9 頁的資源選擇檢查表逐項檢查，然後在第 6 頁勾選下一步。

試用時的資料與權限注意事項
  • 試用一律用虛構資料；確認安全、授權都沒問題前，不放入真實個資。
  • 不要為了試用而把組織帳號的密碼或 API 金鑰貼進任何檔案、AI 對話或 GitHub。
  • 沒有 LICENSE 的專案：可以參考學習，正式使用前先聯繫作者。
